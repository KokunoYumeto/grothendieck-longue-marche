# Final-readiness schema and scope

`scripts/validate_final_readiness.py` is a read-only mechanical gate. It does not open scans, witness files, C notes, or context. It does not determine readings or prove mathematics. It reads output notes only as bytes for SHA-256 and literal marker matching.

## Invocation

```bash
PYTHONDONTWRITEBYTECODE=1 python scripts/validate_final_readiness.py
PYTHONDONTWRITEBYTECODE=1 python scripts/validate_final_readiness.py --output /absolute/output --contract documentation/final_readiness/contract.json
```

The contract path is relative to output. There is no write, audit, freeze, or context-opening option. Success prints JSON with `ok:true`, `written:false`, verified counts, an input fingerprint, and every checked input's SHA-256. Failure prints `ok:false` and exits nonzero. The Python API is `validate_readiness(output, contract)` and raises an error on failure.

The helper uses pinned, output-only `documentation/final_readiness_page_map.json`, derived from page-map identities and the map's SHA-256. It does not need witness files at final delivery. The current page-map metadata fixes 106 pages, with 84 in cote 10 and 22 in cote 12.

## Templates are not evidence

The five JSON files under `documentation/templates/final_readiness/` contain `completed:false` or `approved_by_root:false`, null times/hashes, and incomplete substantive entries. The question template contains one visibly incomplete schema placeholder, which root must replace with the actual required questions. The CHECK_EVENTS template contains the user's five-column header and no events. These templates cannot pass validation. Root should fill them only as the corresponding work actually occurs. No live attestation or check event is generated by this helper.

All documented field sets are exact. Unknown fields, duplicate JSON keys, non-finite JSON numbers, wrong boolean types, unsafe paths, and symlinks are rejected. UTC values may use `YYYY-MM-DD HH:MM:SS UTC` or an explicit UTC ISO timestamp. Dates without time/zone are not accepted. Do not backdate an event or invent a completed review.

## Contract

`contract.json` has these fields:

| Field | Required value |
|---|---|
| `schema_version` | Integer 1. |
| `approved_by_root` | Boolean true only after root approves this coverage contract. |
| `reviewer_id` | Nonempty label used consistently by review attestations and CHECK_EVENTS. |
| `notes_files` | Nonempty unique list of output-relative `.md`, `.tex`, or `.txt` notes deliverables. Source/context/template/archive paths are prohibited. Every declared file is fingerprinted. |
| `standing_question_ids` | Nonempty unique ordered list of root's actual required question IDs. No IDs or questions are invented by the helper. |
| `notation_attestation` | Path to the live notation reconciliation JSON. |
| `notes_coverage` | Path to the live page-notes coverage JSON. |
| `c_notes_review` | Path to the live C-notes review JSON. |
| `standing_questions` | Path to the live standing-question evidence JSON. |

The four live attestation paths must be distinct JSON files under `documentation/final_readiness/`.

## Common review fields

Each attestation has `schema_version:1`, `completed:true`, `reviewed_by` equal to the contract reviewer, and `completed_utc`. Notation reconciliation must be completed after the latest audit and no later than the freeze commit. Research attestations and their individual reviews must be after context opening and not in the future.

Notes coverage, C-notes review, and standing-question evidence also contain `freeze_manifest_sha256`, the exact hash of `documentation/transcription_freeze.json`. Notes coverage additionally binds `combined_sha256`.

### Evidence references

An `evidence_refs` list is nonempty. Every entry has exactly:

```json
{"path":"EXACT_OUTPUT_NOTES_FILE","sha256":"EXACT_NOTES_SHA256","marker":"EXACT_UNIQUE_LITERAL_MARKER"}
```

The path must occur in `notes_files`. The whole file hash must match, and the UTF-8 marker must occur exactly once. The validator does not inspect the prose surrounding it. Different page-coverage entries must use different markers. A convenient root-authored Markdown marker is `<!-- page: EXACT_PAGE_KEY -->`.

If a notes file changes, update the corresponding root-authored evidence hashes before validation. The validator does not update them automatically.

### Notation reconciliation

In addition to common fields:

- `page_keys` is the exact ordered list of all 106 canonical keys.
- `combined_sha256` binds the final consolidated bytes.
- `notation_indices` is exactly two `{path,sha256}` entries, in order: `documentation/notation_occurrences.tsv`, then `documentation/notation_groups.tsv`.
- `reconciliation_summary` is a nonempty root-authored account of the completed review.
- `unresolved_notations` is a list of distinct explicit unresolved items; it may be empty.

The helper verifies hashes and declared completion. It does not reconcile notation itself. The indices must be refreshed after the last page correction and before root finishes this attestation.

### Notes coverage

`pages` contains exactly 106 entries in canonical order. Each has:

```json
{
  "page_key": "EXACT_PAGE_KEY",
  "reviewed": true,
  "reviewed_utc": "ACTUAL_UTC",
  "evidence_refs": [{"path":"NOTES_FILE","sha256":"EXACT_HASH","marker":"UNIQUE_MARKER"}],
  "statement_ids": ["ROOT_DEFINED_STATEMENT_ID"]
}
```

Use `statement_ids` here for mathematical statements covered by the page notes. Each such ID needs a real event using one of the six user-authorized types below, including the authorized background status where appropriate. Bibliographic, transcription, and descriptive notes need no CHECK_EVENTS row: leave this list empty and provide the concrete note reference and review declaration. The page still needs a review and a unique evidence marker. Nonempty IDs must use letters, digits, underscore, period, colon, or hyphen and begin with a letter.

### C-notes review

`folders` covers all 12 mapped folders in order. Each entry has `folder,reviewed,reviewed_utc,source_reference,source_sha256,evidence_refs,statement_ids`. The source reference is the exact metadata name `codex/FOLDER/FOLDER_notes.md`. Root supplies the source SHA-256 and review declaration. **The validator does not open C notes or recompute that source hash.** It verifies the source-reference identity and hash format, the declaration, and exact output-note evidence references.

`statement_ids` may be empty when no mathematical-work event is attached. A C-notes review itself does not require a CHECK_EVENTS row. Mathematical statements listed here need real events using the user's authorized types. This metadata does not substitute for reviewing the source C notes.

### Standing questions

`questions` matches the contract's exact ordered question-ID list. Each entry has:

```json
{
  "question_id": "ROOT_REQUIRED_QUESTION_ID",
  "question_kind": "mathematical",
  "addressed": true,
  "reviewed": true,
  "reviewed_utc": "ACTUAL_UTC",
  "status": "unresolved",
  "statement_ids": ["ROOT_DEFINED_STATEMENT_ID"],
  "evidence_refs": [{"path":"NOTES_FILE","sha256":"EXACT_HASH","marker":"UNIQUE_MARKER"}]
}
```

Root must explicitly set `question_kind` to `mathematical`, `bibliographic`, or `transcription`; there is no inferred or default classification. Status is `resolved`, `partly_resolved`, or `unresolved`. Honest unresolved work is permitted if it is addressed, reviewed, and concretely evidenced.

Mathematical questions need a nonempty statement-ID list and a linked real event using a user-authorized type. Bibliographic questions (including titles, dates, and page counts) and transcription questions need root's concrete notes/evidence reference and `reviewed:true`, but **no CHECK_EVENTS row**. Their statement-ID lists may be empty; any optional identifiers do not create a check-event obligation. No bibliographic or transcription event type is introduced. Manuscript/text review must not be represented as mathematical work. The validator does not judge the substantive answer.

## CHECK_EVENTS.tsv

The exact five columns, in order, are:

```text
statement_id	date	who	type	outcome
```

Every row has five nonempty fields. Dates are explicit UTC timestamps; reviewer labels match the contract; statement IDs must occur in the page, C-notes, or question attestations. Actual mathematical notes statements and mathematical-question IDs need event coverage. Bibliographic/transcription question IDs do not. Identical duplicate rows are rejected, while different events for the same statement are allowed. Outcome is nonempty root-authored text, not a forced conclusion.

The accepted event types are exactly the user's mathematical-work vocabulary:

| Type | Phase and meaning |
|---|---|
| `targeted proof check` | An actual targeted check, with concrete evidence in the linked notes. |
| `independent re-proof` | An actual independent re-proof. |
| `computation or formal certificate` | An actual computation or formal certificate. |
| `used and rechecked in this run` | A statement used and actually rechecked during this run. |
| `carried as background without fault found` | The authorized background status; valid coverage, with no claim of a fresh proof or computation. |
| `refuted` | A refutation with the refined statement ID explicitly recorded in the outcome, or the equivalent type form described below. |

Mathematical notes statements and mathematical standing questions must link to real user-authorized events. All six types are accepted for statement coverage. Background entries are reported separately from performed checks and never described as fresh re-proofs, computations, or rechecks. Bibliographic and transcription questions are exempt from event requirements and instead require concrete reviewed notes evidence. Invented transcription, notation, context-review, C-notes-review, generic mathematical-check, and standing-question-review event labels are rejected. The helper enforces the user's vocabulary, dates and links; root remains responsible for truthful classification and real mathematical work.

These mathematical-work events must be timestamped in the post-freeze research phase, after context opening and no later than completed research attestations. Transcript reading is not logged as a mathematical event.

### Refuted statement ID

For type `refuted`, the outcome must explicitly identify the refined statement. Supported labels include `refined statement ID: S.refined`, `refined statement ID = S.refined`, `refined statement ID S.refined`, `refined SID=S.refined`, `refined_statement_id=S.refined`, or `SID=S.refined`. Label words are case-insensitive; ID case is preserved. Explicit refined labels take precedence over a generic SID label.

Alternatively, the type field may use the clearly supported equivalent `refuted: S.refined`. Its outcome still needs a nonempty account, but the refined ID need not be repeated there. The helper classifies this form as `refuted` without rewriting TSV bytes.

Backticks or quotes around an ID preserve its exact punctuation. For unquoted IDs, terminal sentence punctuation is excluded; quote an ID if a trailing period or colon is part of the identifier itself. Missing, malformed, or conflicting explicit refined IDs are rejected. No extra column, separate check row, or new declaration for the refined target is required.

## Freeze, context, final verification, and packaging

Pending metadata followups at `evidence/audit_metadata_followups.json` block both freeze readiness and final readiness. If the file is absent, absence is recorded for the final package snapshot. If present, it must have schema version1 and an entries list (legacy list form is also read). Entries require unique nonempty IDs. A pending entry must be reconciled through actual explicit root audit history; only then may its status become `resolved` or `applied` with `applied:true`. The checker does not change records, apply corrections, or supply completion declarations. A present resolved followup file is included in the freeze evidence fingerprint and final input hashes.

The gate verifies exact 106 page/record coverage, complete audits in map order, all immutable histories and repeated-audit chains, no unfinished audit, every image-first receipt, the freeze's complete evidence fingerprint, and all 107 frozen hashes. The combined file must equal the exact ordered page bytes.

Context must have exactly one valid `context opened YYYY-MM-DD HH:MM:SS UTC` marker. Its position and timestamp must be after a valid committed freeze. Completion/audit events after freeze are rejected. The helper never opens context.

After all notes and CHECK_EVENTS are complete, root must explicitly run `freeze_transcription.py --verify --write`. The final validator requires the latest recorded hash-verification event to be successful for 107 files, later in the log than context opening, and no earlier in time than the completed notes/checks. It then recomputes all hashes independently. An older verification cannot certify subsequently completed work.

The validator does not create or upload a final ZIP. It returns `input_sha256`, `protected_tree_membership`, and `protected_absent_paths` for the validated snapshot. The packager's `--final` mode requires a successful current readiness result, rejects any required evidence path excluded by packaging, and compares the closed temporary ZIP's actual hashes and protected membership/absence against that result before publication. It never weakens source exclusions to accommodate an evidence path. Preserve the successful report and pause output writes during final packaging. Checkpoint behavior remains unchanged; sources, scans, context, prior archives and raster evidence remain excluded.

## Verification of this helper

The synthetic regression suite is `scripts/tests/test_final_readiness.py`. It constructs 106 invented page identities using the pinned map, with artificial page bytes, audit metadata, receipts, notes, and timestamps in temporary directories. It never invokes live audit/freeze operations, opens sources/images/context, or uses manuscript prose.

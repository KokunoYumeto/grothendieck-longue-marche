# Reconciliation utility

`reconcile.py` is mechanical tooling. It does not inspect ink, run OCR, make readings, or fill missing decisions. Every input decision and check observation must come from an actual visual reader.

Run from the task workspace containing `source/`, `work/`, and `deliverable/`. Alternatively provide `--workspace /absolute/path` before the subcommand.

```bash
python deliverable/scripts/reconcile.py status
python deliverable/scripts/reconcile.py validate 3
python deliverable/scripts/reconcile.py commit 3
python deliverable/scripts/reconcile.py import-check work/scan003_independent.json
python deliverable/scripts/reconcile.py verify
python deliverable/scripts/reconcile.py verify --final
```

`validate` and `commit` default to `work/scanNNN.json`; override with `--file`. The input is either the row list or the object described in `PAGE_READER.md`. Use its `reader` or `who` field to supply model, known effort (or "not exposed"), and actual agent/run. The `commit` option `--who` overrides that declaration. No identity or effort value is invented.

Every page must contain its exact original IDs in order. The first commit is scan 003; later commits must follow the supplied page sequence. A repeated commit of identical rows is safe. Different revisions of a committed page require deliberate amendment and a retained audit history; the script refuses to silently overwrite them.

`commit` writes the full submitted JSON to `audit/scanNNN.json`, stores an auditable transaction receipt under `audit/receipts/`, applies only complete listed source-mark spans to `pages/`, regenerates ordered `decisions.tsv`, appends check events, retains unmarked errors without changing them, appends the page's pattern observations once, records declared reader timing/view counts in `audit/METRICS.tsv`, and writes the page completion to `progress.log` using actual commit time. A receipt allows a repeated identical commit to reconstruct a write interrupted partway through.

`import-check` requires an independent-check object with reader/who, checked_at/finished_utc/date, and rows containing id, reading, crop, confidence, and "observed strokes" or "what the ink shows". It preserves the complete input and adds check events without increasing the initial decision count. It explicitly records disagreements for coordinator resolution.

`verify` checks exact source substitution, original ID order, complete event fields, page progress, and receipt consistency. `--final` also requires all 2,684 marks on all 142 pages. It cannot establish that an ink observation is true; that responsibility belongs to visual inspection.

Source syntax anomalies and literal-pipe handling are documented in `audit/SOURCE_ANOMALIES.md`. Optional row `candidates` metadata may specify actual candidate boundaries where mathematical absolute-value bars share the same pipe character as choice separators. This override remains in the full submission and receipt for review.

A mechanical self-check, run while building the utility, checked escaped-brace parsing, nested source containment, and exact unchanged source segments for all 142 source files. It used sentinel replacements in memory only; no manuscript decision, page file, or ink-check event was generated by that self-check.

Commit and independent-check imports take an exclusive `fcntl.flock` on `work/reconcile.lock`. Checkpoint packaging should hold that same lock while verifying and writing its ZIP. Read-only `verify` does not lock, avoiding a nested-lock deadlock in packaging.

## Disjoint readers on the same page

For a page assigned to two readers, each writes only its assigned contiguous ID subset in a separate `work/scanNNN_a.json` or `_b.json`. Every row must still have its own inspected ink evidence. Merge only after both have finished:

```bash
python deliverable/scripts/merge_readings.py 5 work/scan005_a.json work/scan005_b.json
python deliverable/scripts/reconcile.py validate 5
python deliverable/scripts/reconcile.py commit 5
```

The merge rejects gaps, duplicate IDs, out-of-order subsets, mismatched pages, missing reader identities, and missing/reversed timestamps. It neither fills nor decides any row. The complete half submissions are copied into `audit/parts/` on commit; the merged `row_readers` mapping supplies the actual visual reader for every initial CHECK_EVENTS row. Page elapsed time is earliest declared start through latest declared finish; separate reader intervals remain in the merged audit JSON. Actual views from both readers are counted, including overlapping views; whole-image numeric bounds count as page views rather than crops.

`next_assignment.py` prints the next uncommitted page and exact ID subsets without viewing ink or changing state. Its current automatic policy is three readers for at least 18 marks, two for 6–17, and one for fewer than 6. `--readers 1|2|3` overrides this, and `--scan N` inspects allocation for an explicit page. Every cut advances past nested children so a parent/child pair always stays with one reader. Root coordinates dispatch in source order; allocation alone never authorizes starting a future page.

The merge utility already accepts any number of supplied parts. For a three-reader page:

```bash
python deliverable/scripts/merge_readings.py 10 work/scan010_a.json work/scan010_b.json work/scan010_c.json
python deliverable/scripts/reconcile.py commit 10
```

The example shows syntax only; actual scan eligibility and IDs come from `next_assignment.py` and the committed receipt prefix.

## Recording direct root dispatch

After root actually starts the allocated fresh readers, record their canonical names with:

```bash
python deliverable/scripts/record_dispatch.py 18 /root/scan018_a /root/scan018_b
```

This updates `audit/COORDINATION.json` under the reconciliation lock. It checks the next eligible page and computes the same disjoint ID groups for the supplied reader count. It does not spawn workers, inspect ink, or create decisions. If a peer is later added, record its actual agent and report path in the state as well. Root reviews and commits routine complete pages directly after reading the full row evidence and any independent report. The bounded coordinator remains available for complex reconciliation or source-span issues; it need not add a turn to every page. Visual proof stays with the named actual readers, never with a coordinator who only reads their reports.

## Deliberate amendments of committed marks

A later accepted visual re-proof uses an explicit amendment, never an ordinary page overwrite:

```bash
python deliverable/scripts/reconcile.py amend work/amend_unift_020_021.json
python deliverable/scripts/reconcile.py amend work/amend_unift_020_021.json --apply
python deliverable/scripts/reconcile.py verify
```

The first command validates without changing any artifact. A plan contains a unique `amendment_id`, the independent `report` path, the complete seven-field `expected` current row for each target in original order, a concrete `reason`, and `accepted_by`. It may include a short `reading_guide_addition`. The report must supply exactly those IDs, scans, decisions, readings, confidence, crop coordinates and observed ink, with its actual reader and review timestamps. No replacement is inferred from prose. Full-page validation checks candidate semantics and rejects changes to any unselected mark, including incidental nested replacements.

`--apply` holds the same exclusive reconciliation lock. Before writing effective outputs, it preserves complete original target receipts, page files, consolidated submissions, raw submissions and their revisions, plus the entire original decisions/check-event files, primary metrics and progress log. Immutable copies live under `audit/amendments/<amendment_id>/before/`; exact staged outputs live under `after/`. The unchanged independent report, plan, SHA256 archive inventory, source hashes, before/after rows, actual preparation/application times, and counts are retained in `manifest.json`. A prepared transaction can resume only from exact saved before/after destination bytes. Reapplying an already completed amendment is a verified no-op.

The effective `decisions.tsv` keeps one row per original ID in original order. Initial statement IDs such as `M0334` remain preserved; a corrected statement receives `M0334@v2` (then `@v3` for another accepted amendment). Separate refutation and independent re-proof events link the prior and refined statements using the actual visual reader and actual check timestamp. `audit/STATEMENT_VERSIONS.json` maps each amended stable ID to its current refined statement and evidence row. The full previous CHECK_EVENTS content is retained as an exact prefix when the amendment appends its events. Verification checks archived hashes, source hashes, version links, effective evidence rows, and original primary rows as well as normal source-byte invariants.

Receipts retain `initial_rows` and `initial_submission_rows`; their original metadata and completion timestamps continue to describe the primary reading. Effective consolidated audit submissions identify amended per-row readers and link the separate re-proof. Later commits generate initial check events from the preserved initial rows, so they cannot backdate a refined reading. Later independent imports use the current version ID. Original working submissions and raw parts remain untouched. Amendments do not add initial decisions, reorder completion, or rewrite primary METRICS; their separate review interval and view counts are recorded in WORKFLOW and the amendment manifest.

## Accepting an independent unmarked error before commit

After root reviews and accepts every `other_errors` entry in an independent report, incorporate those entries into the merged current-page workfile with:

```bash
python deliverable/scripts/add_independent_errors.py work/scan027.json work/scan027_peer.json
python deliverable/scripts/reconcile.py validate 27
python deliverable/scripts/reconcile.py commit 27
python deliverable/scripts/reconcile.py import-check work/scan027_peer.json
```

The example documents the actual first use; use the current scan's actual paths. The importer preserves each peer's source report hash, identity, check timestamp and exact accepted error entries in `supplemental_other_error_reports`. It does not alter decision rows, primary parts, reader/timing/view metadata or source files. Exact duplicate entries and provenance records are not added twice. Missing required fields, conflicting scans, a target primary part, or an already committed page cause refusal before mutation. The merged workfile is atomically replaced under the reconciliation lock. Rerunning a primary merge would rebuild its input, so perform this incorporation after the final merge and before commit. Independent row checks are still imported separately after commit.

## Recording completed coordination

After root has reviewed the rows, committed the page and imported every selected independent report, run `python deliverable/scripts/record_completion.py N --notes work/scanNNN_coordination_notes.json`. The optional notes file is a JSON array of coordinator conclusions, not new ink observations. This helper refreshes completion counts from the actual tables and receipts, closes the recorded assignments, and preserves an immutable `audit/revisions/scanNNN_coordination_final.json` before the next dispatch replaces current state. It holds the reconciliation lock and refuses to overwrite a conflicting final archive. Earlier manually archived coordination files retained their dispatch-time counts; their final page conclusions and the authoritative tables/receipts remain distinct.

## Exact aliases in the unmarked-error table

Independent-check imports also append their other_errors observations. Root must review those entries before import, including any overlap with primary observations. The installed scripts/other_error_aliases.py uses audit/OTHER_ERROR_ALIASES.json to map only explicitly reviewed, exact four-field rows to retained canonical rows. Unknown wording variations remain distinct; matching scan and reading alone never merges errors. Both commit and import require the existing table to be canonical and preserve raw submitted reports. A newly identified semantic duplicate requires a reviewed registry update and retained before/after audit transaction, as documented in audit/other_error_normalizations/OE0001_exact_aliases_042_044_046. Verification checks canonical uniqueness, not completeness against every report.

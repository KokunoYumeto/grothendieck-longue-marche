## Full-source replay restoration audit

`code/pbc_restore_full_source_replay.py` resolves all paths relative to the extracted archive. Its recipe names the exact corrected finite DAT input, replay C++ source, executable and both collector headers, and hashes each. The source includes no missing private project file: the bitset header includes the retained control header, which includes only standard C++ headers. If the recorded executable is absent, nonexecutable or has a different hash, the helper compiles the retained source using g++17, GMP and zlib. The fallback compiler arguments include the source directory explicitly. No external raw trace, live basis, scratch capture, network download or absolute original path is needed for reconstruction.

The replay runs the complete original source-row collection and exact reducer, truncating only after the recorded complete proof-record count. Source rows are regenerated, rather than replaced by a promised future calculation. Before a replay recipe may replace the large stream in an archive, the verifier must compare every regenerated decoded byte with the immutable closed original capture and verify its total hash/count. The stored recipe must then say that this entire comparison passed. The helper reconstructs all original decoded bytes into a fresh gzip and checks their hash/count; the gzip wrapper is a new container, while the original wrapper's hash and length remain in the recipe. A successful storage comparison is not a positive mathematical certificate.

The exact whole-stream replay result is recorded separately in `code/pbc_suffix3_v2_full_replay_verification.out` and, only after a complete pass, `code/pbc_suffix3_v2_full_replay_recipe.json` plus its transform ledger.
